# start-issue：Issue から作業を始める

このリポジトリの残作業は GitHub Issue で管理している。
1 つの Issue が 1 つの作業で、本文に背景、やること、完了条件、前提、参照、結果の記録の場所が書いてある。
このスキルは、着手できる Issue を選び、担当を明らかにし、作業ブランチを用意してから作業に入るためのものである。
別のセッションが作業を引き継いでも、Issue と作業ブランチを見れば続きから始められる状態を保つ。

## Issue の約束事

| ラベル | 意味 |
|---|---|
| `task` | 残作業として管理している Issue。このスキルが扱うのはこのラベルの Issue だけである |
| `hardware` | 印刷や実機での作業が要る。Claude だけでは完了できない |
| `in-progress` | だれかが作業中である |

本文の「## 前提」節に `- #N` の形で、先に閉じている必要のある Issue が並ぶ。
実機の結果は、ユーザーが Issue のコメントに書く。
多くは [実機での確認手順](../../../docs/physical-test-procedure.md) の末尾にある記録表を埋めたものである。

## 1. 状態を確かめる

```bash
gh auth status
git status --short
git fetch origin
```

作業ツリーに未コミットの変更があれば、どの作業のものかをユーザーに確かめ、片付くまで先へ進まない。
別の作業の変更を新しいブランチへ持ち込むと、コミットがどの Issue のものか言えなくなる。

## 2. Issue を選ぶ

```bash
gh issue list --label task --state open \
  --json number,title,labels,assignees,body
```

- 引数やユーザーの言葉で番号が指定されていれば、その Issue を選ぶ。
- 指定がなければ、次の条件をすべて満たす Issue を着手候補とする。
  - 「## 前提」節に並ぶ Issue がすべて閉じている（`gh issue view N --json state` で確かめる）
  - 担当がいないか、担当は自分（`gh api user -q .login`）だけである
  - 自分以外の担当者による `in-progress` の印がない
- 候補が 1 つならそれを選ぶ。複数あれば、番号、タイトル、`hardware` の有無を示してユーザーに選んでもらう。候補がなければ、開いている Issue と、それぞれが止まっている理由（前提が開いている、他の人が作業中）を報告して終える。

指定された Issue の前提が開いている場合は、開いている前提を示し、それでも進めるかをユーザーに確かめる。

## 3. アサインして作業ブランチを切る

```bash
gh issue edit N --add-assignee @me --add-label in-progress
```

作業ブランチは `issue-N-<英小文字とハイフンの短い名前>` とし、`origin/main` から切る。
同じ番号のブランチがローカルかリモートにすでにあれば、新しく切らずにそれへ切り替える（前のセッションの続きである）。

```bash
git branch -a --list "*issue-N-*"
git switch -c issue-N-<name> origin/main   # 既存がなければ
```

セッションが専用の worktree で動いている場合も、ブランチの命名は同じにする。

## 4. 作業の内容を読む

```bash
gh issue view N --comments
```

本文の完了条件、参照にある文書の該当箇所、コメントに書かれた実機の結果をすべて読む。
完了条件のうち、すでに満たされているもの（チェック済み、または前のセッションのコミットで済んでいるもの）を確かめ、残りを作業の一覧にする。
仕様書 [docs/specs/smartphone-holder-adapter.md](../../../docs/specs/smartphone-holder-adapter.md) の「やらないこと」と「検討した代替案」も読み、棄却済みの案に流れ込まない。

## 5. 作業する

### `hardware` の Issue

印刷、組み立て、計測はユーザーの手で行う。Claude が行うのは次の 3 つである。

1. **案内**：手順書の該当する段階を示し、ユーザーがその場で使えるように、確かめる項目と合格の基準を短くまとめて伝える。結果は Issue にコメントで書いてもらうよう頼む。
2. **反映**：コメントに結果が書かれていれば、その値で `cad/params.py`、README の結果欄、仕様書の手順表を更新する。値を変えたら `uv run python scripts/build.py` と `uv run pytest` を通す。
3. **判断材料の用意**：不合格の項目があれば、手順書の調整表に従った次の値を提案する。調整表で対処できない不合格（外れ、回転、水平が保たれないなど）は、設計の見直しとして別の Issue に切り出すことを提案する。

結果がまだ書かれていなければ、案内までで止め、Issue に「作業中」のまま残す。
実機で確かめていないことを、確かめたかのように書かない。

### それ以外の Issue

完了条件を 1 つずつ満たし、そのたびに検証する。

### 共通の約束

- 日本語の文書を書いたら `japanese-document-writing` スキルに従い、textlint の指摘をゼロにする。`--fix` は使わない。
- コミットは既存の `git log` の型に合わせる。日本語で「1 行要約 / 空行 / なぜそうしたかの散文 / 変更点の箇条書き / 検証結果の 1 行」とし、末尾に `Co-Authored-By` トレーラーを置く。本文に `#N` を書き、どの Issue の作業かを辿れるようにする。
- Issue の範囲外で見つけた問題は直さず、新しい Issue（`task` ラベル付き）として提案する。

## 6. 区切りをつける

作業の区切りごとに、Issue に進み具合をコメントする。
次のセッションが読めば続きから始められるように、済んだこと、残っていること、ブランチ名を書く。
本文の完了条件のチェックボックスは、満たしたものだけにチェックを入れる（`gh issue edit N --body-file`）。

完了条件をすべて満たしたら、次の順に進める。
プッシュとプルリクエストの作成は外から見える操作なので、ユーザーの了承を得てから行う。

1. ブランチをプッシュする。
2. 本文に `Closes #N` を書いたプルリクエストを `main` に向けて作る。
3. `in-progress` ラベルを外す（`gh issue edit N --remove-label in-progress`）。

作業を途中でやめる場合は、ラベルと担当をそのまま残し、進み具合のコメントだけを書いて終える。
